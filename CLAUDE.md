# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

See `PROJECT_STATUS.md` for product context, what's built vs. pending, and infra/account state — this file is strictly about the code.

## Commands

- `npm run dev` — start the dev server (auto-falls back to port 3001/3002 if 3000 is busy)
- `npm run build` — production build (also what Vercel runs on every push to `main`)
- `npm run lint` — ESLint
- `npx tsc --noEmit` — typecheck

There is no automated test suite in this project. Verify changes by running the dev server and exercising the flow (curl against API routes, or a browser for pages) — not with a test runner.

## Database migrations

No ORM, no migration tool. `schema.sql` is the fresh-install source of truth; `migrations/*.sql` are the incremental changes already applied, in order, to the live Supabase database. A schema change needs both a new `migrations/NNNN_*.sql` file and the matching edit to `schema.sql`. These have to be run manually in the Supabase SQL editor — there's no way to execute DDL from this environment or from the app itself (only the REST/service-role client, which can't run raw SQL).

## Architecture

**Everything is server-only.** `src/lib/supabase.ts` exports one Supabase client built with the `service_role` key (bypasses RLS) and forces `cache: "no-store"` on every request it makes. Never import it from a `"use client"` component — there is no client-side Supabase usage anywhere in this codebase, by design. RLS is enabled with no policies (default-deny) on every table as defense-in-depth; since the app only ever reaches the DB through this service-role client, RLS is otherwise irrelevant to it.

**No auth system exists.** Creators don't log in. Each creator gets a `management_token` (random string, `creators.management_token`) generated at signup; `/manage/[token]` is the only thing gating availability edits. Treat it like a bearer credential, not a session.

### Booking lifecycle

This is the core flow and spans most of `src/app/api/`:

1. **`/api/creator/onboarding`** — creates a `creators` row. The slug is client-chosen (not server-generated); validated for uniqueness with a pre-check plus a race-safe fallback on the `23505` unique-violation from the insert itself.
2. **`/api/creator/availability`** (used by `/manage/[token]`) — replaces a creator's full set of `weekly_availability_rules` (one row per day-of-week). **Availability is never materialized into concrete slots.** `src/lib/availability.ts#generateAvailableSlots` computes real bookable datetimes live, for a rolling 30-day window in `Europe/Paris`, from the rules (plus date-specific overrides — see below) minus existing `bookings` in that range. This is why editing a schedule can never corrupt an already-booked slot — bookings live in a separate table that nothing here touches.
   - **`/api/creator/availability-overrides`** (used by the calendar in `/manage/[token]`) layers date-specific exceptions on top: an override for a given `date` — either a custom window (`is_available: true`) or a full block (`is_available: false`) — always wins over the recurring rule for that date, resolved once in `resolveWindowForDate()` and reused by both `generateAvailableSlots` and `isSlotWithinRules` so the two can't disagree. No override for a date = fall back to the weekly rule, same as before.
3. **`/api/checkout`** — re-validates the requested `slot_time` server-side via `isSlotWithinRules` (never trusts the client's chosen slot), inserts a `pending` booking (capturing `amount_cents` = the creator's `hourly_rate_cents` *at that moment*, independent of later rate changes), creates a **plain** Stripe Checkout Session (charged to the platform account — no destination charge, no Connect requirement) and stores `booking_id` in the session metadata. Rolls back (deletes) the booking if the Stripe step fails, so a failed checkout can't leave an orphaned row blocking that slot forever. An **abandoned** checkout (session created, never paid) is a separate case handled by `/api/cron/expire-pending-bookings` — see below.
4. **`/api/webhooks/stripe`** — the only place a booking moves `pending` → `confirmed`. Verifies the Stripe signature against the **raw** request body (`request.text()`, not `.json()` — parsing first breaks the signature check). On `checkout.session.completed`, generates a Jitsi room (`src/lib/jitsi.ts` — just a URL scheme, no API or key needed) and emails both parties (`src/lib/email.ts`) links to `/call/[bookingId]?token=...`, never the raw Jitsi URL.
5. **`/call/[bookingId]`** — gates entry to the call by time window (opens 15min before `slot_time`, closes `SLOT_DURATION_MINUTES` after — exported from `availability.ts` so both places agree on how long a call is). The role (`creator`/`customer`) is never trusted from a query param — `src/lib/call-tokens.ts#resolveRoleFromToken` derives it from an HMAC token (`CALL_TOKEN_SECRET`) baked into each party's own link; the two emails for the same booking used to differ only by a bare `?role=` string, which either party could edit to claim the other's role. Clicking "Join" calls `/api/bookings/join` with that same token (re-validated server-side, not the resolved role) and sets `creator_joined_at`/`customer_joined_at` **once** — first join wins, since a later reconnect must never push the recorded timestamp later than the true arrival (that's exactly what arbitration measures).
6. **Arbitration** (`src/lib/arbitration.ts#arbitrateBooking`) is the single source of truth for the business rules; two thin routes call into it and must stay thin:
   - **`/api/webhooks/arbitration`** — manual/simulated trigger. Accepts explicit join timestamps in the request body, writes them, then calls `arbitrateBooking`. Predates real presence-tracking and is still useful for testing a scenario directly.
   - **`/api/cron/arbitration`** — the real automatic trigger, hit every 5 minutes by the GitHub Actions workflow at `.github/workflows/arbitration-cron.yml`. Scans `confirmed` bookings whose call window has passed and arbitrates each using whatever presence was actually recorded in step 5.
   - Rules: creator absent or >10min late → plain refund (resolved via the Checkout Session's `payment_intent` — `stripe_payment_id` stores the *session* id, not the intent id, so the session must be retrieved first) → `no_show_creator`. Creator on time but customer absent or >15min late → `no_show_client` (funds stay captured). Both on time → `completed`. Idempotent — bookings already in a terminal status are skipped, so replayed events can't double-refund.
   - The payout attempt (see point 7) is wrapped in its own try/catch inside `arbitrateBooking` — a transfer failure (e.g. insufficient Stripe balance) must not crash the whole function before the status update and outcome emails happen. Learned the hard way: it used to throw uncaught and silently skip notifications.
7. **Payouts** (`src/lib/payouts.ts`) — creators are paid 90% via **separate charges and transfers**, not a destination charge at checkout time (deliberately, to defer requiring Stripe Connect onboarding until it actually matters — see `PROJECT_STATUS.md`). When arbitration lands on `completed`/`no_show_client`, it calls `tryPayoutBooking`: if the creator's Connect account is already `payoutsEnabled` (`src/lib/stripe-connect.ts#getConnectStatus`, a live API check, not cached), transfer immediately; otherwise leave `stripe_transfer_id` null. `/manage/[token]`'s page load calls `releasePendingPayouts` whenever it sees the creator is now Connect-ready — this is what sweeps up money that was earned before they finished onboarding (typically fires the moment they land back from Stripe's hosted onboarding, since that IS the `return_url`). If a creator never comes back to finish onboarding, `/api/cron/stripe-connect-reminders` (same GitHub Actions schedule) nudges them by email — throttled to once every 3 days per creator via `creators.stripe_connect_reminder_sent_at`, since the cron itself runs every 5 minutes.
8. **`/api/cron/expire-pending-bookings`** (same GitHub Actions schedule) — a `pending` booking with no follow-up (customer abandons the Stripe Checkout tab) would otherwise block its slot forever, since nothing else ever moves it out of `pending`. Deletes any `pending` booking whose `created_at` is more than 10 minutes old, and proactively calls `stripe.checkout.sessions.expire()` on its session first — otherwise a customer who still has that abandoned tab open could complete payment *after* we've deleted the booking, capturing real money with no booking left to attach it to. The delete itself is conditioned on `status = 'pending'` (not just `id`), so if the confirmation webhook races in first, the delete just affects 0 rows instead of destroying a booking that just got confirmed.
9. **Emails** (`src/lib/email.ts`) — every send goes through one `renderEmail()` layout (logo + a single indigo accent, deliberately not trying to replicate the app's gradients/blur — most email clients strip that anyway). `arbitrateBooking` calls the outcome email (`sendNoShowCreatorEmails` / `sendNoShowClientEmails` / `sendReviewRequestEmail`) directly after persisting the status. Reminders are separate: `/api/cron/reminders` (same GitHub Actions schedule as arbitration) scans for bookings crossing the 24h- or 1h-before threshold. Its two windows are **non-overlapping by construction** (each has a lower bound at the previous window's threshold) — a naive "slot_time within Nh" check for both windows independently double-sends to anything under 1h away, since that also satisfies "within 24h."

### Known gotchas (read before "fixing" these again)

- **Next.js's fetch Data Cache serves stale Supabase reads**, and this survives even a full `next dev` restart (it's persisted to disk in `.next/cache`). `export const dynamic = "force-dynamic"` on a page is not reliable enough on its own to prevent it — the real fix is the `cache: "no-store"` set on the Supabase client's `fetch` in `src/lib/supabase.ts`. If data looks stale, check that first, not the query logic.
- **`vercel.json` must declare `"framework": "nextjs"`.** The Vercel project was created via `vercel project add` rather than the normal interactive flow, which left the dashboard's Framework Preset as "Other" — without the override, builds fail looking for a `public/` output directory.
- Deploys are git-based: pushing to `main` on `github.com/bastaga15/yessrr` auto-deploys to Vercel production. `vercel --prod` from the CLI is no longer the normal path.
- **A column having a `default` in `schema.sql` does not mean the live table has it.** `creators.management_token` was added to the live DB via an incremental `alter table` migration that backfilled existing rows but never set a `DEFAULT` — every insert had to supply its own value, and the onboarding route didn't, so every signup 500'd until this was caught and fixed (the route now generates the token in code; the DB default was also patched in migration 0006, but don't rely on schema.sql alone to know what a column does live — check `migrations/` for what was *actually* run).
- **Stripe test-mode transfers need "available" balance, not just "pending."** A normal test-card charge sits in pending balance for ~7 days (simulating real settlement) and `stripe.transfers.create` will fail with "insufficient available funds" against it. To test payouts locally, fund the test balance directly with the special bypass token (`stripe.paymentIntents.create` using `payment_method_data: { type: "card", card: { token: "tok_bypassPending" } }`) rather than a normal test card.
